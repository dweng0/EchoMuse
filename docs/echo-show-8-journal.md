# Echo Show 8 (crown) journal

Chronological log for the `echo-show-8-support` branch — crown-specific work split out of the main `JOURNAL.md` on 2026-08-27 so the multi-platform effort has its own record, separate from biscuit's. Same format, same rules as the parent file. Continuation entries (status-bar work, fresh-provisioning) live in `docs/echo-show-8-status-bar-handoff.md` and the other handoff docs until they get folded back in here.

- 2026-08-26 (**crown's mic and speaker went from spike to a proven voice loop on real hardware, in one session, on `echo-show-8-support`**): started from a stray uncommitted `internal/profile/` package — a runtime `Detect()` picking board behaviour off `ro.product.device` — that turned out to directly contradict ADR-0001 (one binary per board, chosen by build tag, no runtime "which board am I" branching), already decided on this branch. Dropped it and wrote the real thing: crown-tagged `PcmMicrophone`/`PcmSpeaker` over `internal/alsa` (no cgo, no GoTinyAlsa — that binding has never touched this driver), a `beamEngine` interface so the mic pipeline in `data.go` (the most delicate hot loop in the binary) needed no per-board branching of its own, and the buttons/LED/capabilities split the same way — `!crown` as the default tag rather than `server`, because `internal/server` and `internal/client` are host-tested with no board tag at all and biscuit has to stay what a bare build produces.

  **Every one of the real bugs was invisible from the host, and there were five of them.** `go build/vet/test -tags crown` was clean throughout; none of this showed up until the binary was actually pushed to a real Echo Show 8 over adb. HW_PARAMS rejected periods=8 (a checkers-derived guess) outright despite every individual field being in HW_REFINE's reported range — individual-dimension ranges don't imply every combination is jointly achievable, and `internal/alsa.Open()` sets each param via `setExact`, not "nearest". periods=5, the exact value `capture_mics` had proven, opened cleanly. Reading one 512-frame period at a time then stalled on nearly every call (66-84ms gaps chasing 32ms batches) — fixed by reading the whole ~160ms ring per call, the same batching CLAUDE.md already documents for biscuit's GoTinyAlsa binding and evidently the same MT8163 scheduling floor. That fix was itself incomplete: a single `Read()` on a buffer that size can legitimately short-read, and AEC caught the resulting misalignment ("1068b is not a multiple of the 1024b speex frame") and bypassed itself — `io.ReadFull` was the actual fix, since `alsa.PCM.Read` already matches `io.Reader`. And two mixer-control bugs, both the same shape: `internal/server/volume.go` and `cmd/server.go`'s ADC-gain path were hardcoded to biscuit's control index and control names respectively, so on crown they hit `Pmic_Anc_Switch` (a different control entirely, index reuse) and produced "2 values given, but control only takes 1" on every connect. Board-scoped the same way as everything else — named controls (`DAC1 Playback Volume`, `ADC_A/B ...`) for crown, confirmed live with `tinymix`.

  **The false alarm is worth recording as its own lesson.** Mid-session, both crown's wake detection and Winston's (a working biscuit device on the same controller) appeared dead at the same time, and killing crown's process was immediately followed by Winston answering again — read in the moment as crown having crashed the shared controller process. Pulling the actual controller logs (`ssh` to the box the container runs on, found via `~/.ssh/config`) showed the opposite: Winston had never stopped, full turns logged continuously through the whole window, no traceback anywhere. The correlation was coincidence, not causation, and crown's wake detection was firing at 0.7-0.99 the entire time — the real, boring reason nothing audible happened was that Home Assistant had never been pointed at crown's freshly-allocated ESPHome port, a one-time integration step, not a bug. Costly reminder that "it started working when I stopped X" is not evidence X was the cause, and that this project's logs answer that question directly if you look before you conclude.

  **Fixing that surfaced a real controller-side bug, in code untouched by any of the above.** Home Assistant's "Secure link" action (push TLS creds over the shell plane, bounce to `wss://`) silently failed on crown — `POST` returned 200, two shell sessions ran, and the target directory stayed empty. `_stream_file_to_device`'s decoder-detection tries `busybox base64`, then python3, then python, and never plain `base64` — and crown, LineageOS toybox userland, has no busybox at all despite `/system/bin/base64` working fine (confirmed by hand: `echo dGVzdA== | base64 -d` → `test`). The failure was invisible in `docker logs` at first because `_run_secure_link` reports failure through `_push_log_event` (the dashboard's per-device log), not the process's own stdout — found by grepping for "decoder" rather than the device ID. Added a plain-`base64` branch between busybox and python3; every other caller of `_stream_file_to_device` (the provisioning wizard's binary/OWW pushes, OTA) gets the same fallback for free, since this was never secure_link-specific. Verified by hot-patching the running container and re-running secure_link live — `Decoder: base64 -d`, ca.pem+token landed, device redialed wss. The hot patch does not survive the next `docker compose pull`; the fix is committed but needs a real controller release to reach the published image.

  **The controller's own Python test suite was not run until near the end of the session, and it caught a real regression the moment it was.** Splitting `capabilities()` off `control.go` into per-board files (hours earlier, for the crown work) broke `test_capabilities.py`, which parses `control.go`'s source text directly to get the device's capability vocabulary — exactly the kind of drift the test exists to catch, aimed at the wrong side this time, since the refactor was legitimate and the test needed to follow it. Fixed by pointing it at `capabilities_default.go` (still biscuit's full list, still the right ground truth — crown's is a strict subset). `go test`/`go vet` had been run repeatedly throughout; `pytest controller/tests/` had not, and should have been step one on any change touching shared controller code rather than something found by accident while chasing an unrelated bug.

  **State at end of session**: full voice loop proven repeatedly on real hardware — wake word → controller OWW → HA Assist → STT → TTS → spoken reply through crown's own speaker, including a correctly-handled barge-in — over `wss://` with TLS credentials installed. A single `provision_crown.sh` (push binary, optional TLS, minimal autostart `.rc` — no A/B slots, no log rotation, deliberately less than biscuit's `start_server.sh` since crown has no fielded-OTA story yet to justify it) installs and starts it in one pass, verified live; found and fixed `pkill -f` hanging outright on this device's toolbox along the way. Both host suites green (`go test`/`go vet` untagged and `-tags crown`; `pytest` — 734 passed). Still open: the `.rc` install has never been proven across an actual reboot; quiet-room/across-room SNR is still not properly measured (five trials with no clean miss is not a curve); the crown action button reports `KEY_POWER`, which does not match `pkg/buttons.MuteClick`, so it does not yet toggle mute; nothing here has been opened as a PR against `main`. Nine commits, all on `echo-show-8-support`.

- 2026-08-26, later (**the `.rc` install's open question from the last entry answered — it doesn't survive a reboot, and the reason is Android's, not ours — plus a live instability that's still unexplained**): confirmed dead on hardware, live: init's `service` directive refuses to execve anything under `/data/local/bin`, "Permission denied", exit 127, with SELinux confirmed Permissive (ruled out directly, not assumed) — a hard Android restriction on init exec'ing untrusted `/data` binaries, independent of SELinux mode. biscuit never hits this because `start_server.sh` runs as a Magisk `service.d` script, and Magisk's own daemon launches those, sidestepping raw init entirely. crown has real root (userdebug `adb root`) but no Magisk at all, so that escape hatch doesn't exist here. Standard fix on stock/non-Magisk Android: an APK with a `BOOT_COMPLETED` receiver launching the binary as a foreground service, since ordinary app execution from `/data` has none of init's restriction. Recorded first as its own commit, then built out this session.

  **Built `device/crown_launcher/` with no gradle, no Android Studio** — two Java classes and a manifest, so a gradle/AGP project would dwarf what it builds. `build.sh` goes straight `aapt2 link` → `javac` → `d8` → `zipalign` → `apksigner`, against a minimal `cmdline-tools` + `platforms;android-30` + `build-tools;30.0.3` install (crown reports API 30 live; matched rather than guessed). `BootReceiver` calls `startForegroundService`; `ServerService` execs `/data/local/bin/server` with stdout/stderr redirected to the same `/data/local/tmp/echomuse.log` path `provision_crown.sh` already tails, `START_STICKY` so Android restarts the service (and the child) if either dies — deliberately as minimal as `echomuse_crown.rc` was for the same reason: one dev unit, no fleet yet.

  **First real gap: a freshly-installed app never receives `BOOT_COMPLETED`.** Android withholds implicit broadcasts from an app in the "stopped" package state until it has been run at least once — confirmed live (`dumpsys package` showed `stopped=true notLaunched=true`; installed, rebooted, nothing started). `am start-service` alone hit `Error: app is in background uid null` (the same background-start restriction real `Context.startService` calls face from Android 8+); `am start-foreground-service` is the shell equivalent of `startForegroundService` and both starts the service AND clears the stopped flag permanently. `provision_crown.sh` now calls it once at install time — this one line is the actual fix for "we lose the connection script on reboot", not the APK by itself. The dead raw-`init.rc` install step came out of the script entirely (proven non-functional above; no reason to keep pushing a file that does nothing).

  **Second gap, found by tracing a `Failed to initialize Microphone: permission denied` after the launcher was otherwise confirmed working**: the exec'd binary runs as the app's own sandboxed uid (`u0_a148`), not root, and `/dev/snd/*` / `/dev/input/*` are `system:audio` / `root:input`, mode `0660` — no supplementary group for a third-party uid. Two wrong turns before the real fix, both worth keeping: (1) granted `android.permission.RECORD_AUDIO` and checked `id u0_a148` after — no `audio` gid appeared, confirming that permission only gates the Binder-mediated `AudioRecord` path and has nothing to do with raw `/dev/snd` file access, which this daemon uses directly (same as biscuit's tinyalsa approach). (2) considered making the launcher a `/vendor/priv-app` privileged app, and stopped before building it — privileged-app allowlisting only ungates Android *permission* checks, not Linux device-node gid membership, which for real system audio processes comes from a build-time AID baked into `android_filesystem_config.h`, not something a pushed APK can acquire after the fact. The actual fix: crown has no separate vendor partition at all (`/vendor` is a symlink to `/system/vendor`, confirmed via `stat`), so the live rule lives in `/system/etc/ueventd.rc`; patched `/dev/snd/*` and `/dev/input/*` from `0660` to `0666` directly (original backed up as `device/crown_launcher/ueventd.rc.crown-orig`), pushed via `adb remount` + `adb push`. Survives a normal reboot and even a factory reset (both only touch `/data`, not `/system`); will NOT survive a vendor/ROM reflash, same durability tier as the launcher APK itself.

  **Third gap, found chasing "mDNS never finds the controller" even with the node-permission fix in**: `tcpdump` on crown's `wlan0` showed the controller's own periodic mDNS announce arriving fine — ruling out the network path — but a 25s targeted capture for outbound traffic from crown's own IP on port 5353 showed zero packets. The app's uid had no `inet` gid (3003) — the manifest never declared `android.permission.INTERNET`, so Android's netfilter owner-match rules silently drop every `socket()` call for that uid, at the kernel level, with no error surfaced to the process. This blocked not just mDNS but would have blocked the controller WebSocket dial identically — a single missing manifest line was going to make the entire launcher pointless once autostart itself worked. Added the permission, confirmed `dumpsys package` reporting `gids=[3003]`, and the full chain came up immediately: registered, config pushed, `Winston` OWW model loaded, mic streaming — all from the app path, no scripts.

  **Then it froze the device outright, three times, and the cause is not fully pinned down.** First freeze: right after `adb reboot` was issued while the daemon was actively streaming through the AEC pipeline — plausibly Android's shutdown sequence stalling on a raw ALSA fd our exec'd process (no real Android service lifecycle, no clean-release hook for a reboot signal) never released properly. Second freeze: spontaneous, sometime after a normal boot settled, no reboot in flight and no confirmed concurrent activity — unexplained. Third freeze: within ~15s of re-enabling the launcher, coincident with the user actively playing YouTube through the browser (`mediaserver` live) — initially reasoned as the daemon's `stop media`/`stop mixer` calls needing root and failing silently under the app's uid, which turned out to be **wrong**: `pcm_speaker_crown.go`/`pcm_microphone_crown.go` never call `stop` on anything — a comment in the mic binding already records that `stop mixer` returns "exit status 1" on this platform (no such service) and that "nothing in the audioserver family may ever be added here", because stopping it on real Android 11 breaks the system rather than freeing the audio path the way it does on FireOS. So freeze #3 isn't a permission gap in our own code — it's the same **already-documented** LineageOS/crown fragility above ("capture works for the first recording after boot, then goes silent until `audioserver` restarts", reported on XDA) escalating from "goes silent" to "hangs the board" under real concurrent load. Isolation test: launcher disabled, device idle and untouched, stable 11 minutes straight (no re-enumeration, no drop); re-enabled, froze within 15s while YouTube was playing. That rules the launcher/autostart mechanism itself IN as fine and points at continuous raw-ALSA use on this ROM as the live suspect — but freeze #2's lack of any known trigger means "needs concurrent Android audio" is shown sufficient, not necessary, and the honest state is one unconfirmed instability with no kernel log from any of the three hangs (`adb` was already gone by the time each one was noticed). Next real step, not yet done: catch `/proc/last_kmsg` or pstore output immediately after a hang, rather than guessing further from correlation alone.

  **State at end of this entry**: `crown_launcher.apk` + the ueventd/INTERNET fixes solve everything the original raw-init problem was about — install once, survive any future reboot, no scripts, full controller handshake proven live from the app path alone. What's now blocking is new and more serious: the daemon does not appear to survive running for long under this launcher, for a reason not yet captured in a log. Do not consider crown's autostart "done" for anything beyond a supervised demo until that's root-caused.

- 2026-08-26, later still (**the freeze root-caused via pstore, six candidate fixes scoped and two field-tested live, and the winning one built end-to-end**): picked up the previous entry's open freeze cold. First move was a doc, not code — `docs/echo-show-8-freeze-scenarios.md` laid out six independent fix directions (stop holding the speaker open; find a shared/dmix ALSA path; route playback through Android's own audio API; patch the HAL/kernel via custom recovery; a full custom ROM; detect-and-recover) before touching any of them, specifically so four could be spiked in parallel by subagents rather than explored one at a time. Prior-art search found nothing — no existing fix anywhere for the exact `mtk_pcm_I2S0dl1` underflow/retry-storm signature, though the milder "capture silent after first recording until `audioserver` restarts" bug already in `docs/echo-show-8-hardware-map.md` is confirmed live and unsolved on the same XDA threads, corroborating that this is the same root fragility at a lower severity. The shared/dmix path turned out not to exist at all: `internal/alsa` talks straight to the raw hw node, AudioFlinger's own mixing happens upstream of the HAL in userspace, and there's no kernel-level node a second client could join — closed for good. Opening the speaker on demand (closing between turns) was judged weaker than it looked: the pstore evidence showed *mediaserver* retrying against a path *we* held open forever, so shortening our own hold only narrows the collision window, it doesn't remove the condition — parked. Routing crown's speaker output through Android's own audio API was the strongest lead precisely because it hands the collision to the party that already knows how to arbitrate it, instead of trying to time around the same shared resource ourselves.

  **Before writing any of that code, answered the one question that could have killed it for free**: does this SoC/ROM actually grant `AudioTrack`'s low-latency path, or silently fall back to the shared legacy mixer (which would have made barge-in worse, not better)? Built a two-minute throwaway (`AudioProbeReceiver`) rather than assume either way — `getPerformanceMode()` came back exactly as requested, native fast-mixer period 16ms, tone audibly heard on the real speaker. Worth the twenty minutes: a `PERFORMANCE_MODE_NONE` result would have changed the whole cost/benefit call before a single line of the real service existed.

  **Built it — `PlaybackServer.java` (crown_launcher) + `socket_pcm_crown.go` (device) — and every step was tested live before being committed, per this session's own instruction to keep commits revertible.** `pcm_speaker_crown.go`'s `Init()` no longer opens `/dev/snd` at all on crown; it dials a socket to crown_launcher's `AudioTrack`-backed service instead, behind a small `pcmWriter` interface so the mixer/duck/ring-buffer code above it needed zero changes. Three real bugs found and fixed by testing, not by reasoning about the code in advance:

  1. `LocalServerSocket`'s attempt at filesystem-namespace silently became abstract-namespace instead — its String constructor only ever binds abstract, and `LocalSocketAddress(...).getName()` just returns the raw name, dropping the intended namespace. Caught via `/proc/<pid>/net/unix` showing an `@`-prefixed entry where `ls`/`find` found nothing. Not worth fighting: abstract sockets need no stale-file cleanup and aren't gated by filesystem permission bits at all, which only strengthened the answer to "does this work across both the app-uid and root-exec launch paths" (yes, trivially, for a reason neither path originally anticipated).
  2. A 25ms write deadline mistook ordinary `AudioTrack` backpressure for a dead connection and thrashed reconnects continuously — raw ALSA's blocking `Write` used to pace `silenceLoop` for free, and nothing replaced that pacing source when the write moved to a socket. Raised to 500ms; ruled out as *the* cause but didn't fully fix the drops.
  3. **The real cause, and the one that briefly produced a false and much larger conclusion**: with the deadline fixed, connections still died reliably after ~0.6–1.3s of streaming, reproducible on both `PERFORMANCE_MODE_LOW_LATENCY` and `PERFORMANCE_MODE_NONE`, with zero errors anywhere in the system log at the exact stall moment — a genuinely silent wedge that looked, for a good chunk of the session, like proof that sustained `AudioTrack` streaming itself doesn't survive on this ROM (which would have sunk the whole approach). Bypassing `AudioTrack.write()` entirely — discard the bytes, do nothing else — ran clean for 6+ seconds with zero drops, isolating the fault to *how* the write was being driven rather than to `AudioTrack`/the HAL. Root cause: the Go writer had no pacing of its own, so it produced whatever the socket's backpressure allowed — several periods in a burst, then a stall — instead of one period every ~32ms. Adding explicit real-time pacing to `socketPCM.Write` (one period every `len(buf)/48000/4` seconds, matching the ALSA config exactly) fixed it outright: 2+ minutes sustained, one connection, zero drops, cross-checked against the daemon's own independent `[mic] clock` line as a second clock source. **Worth recording at length because the wrong conclusion was completely convincing in the moment** — reproducible, silent, present under both performance modes — and would have wrongly closed off this whole direction if accepted instead of chased one step further with a bypass test.

  **Then the actual test that mattered**: with the daemon's real (non-probe) speaker plane running continuously through the fixed socket + `AudioTrack` path, browser audio playing concurrently on the device, and a volume-button press exercised mid-test — 30+ seconds, zero freeze, zero drops, one stable connection, clean pstore both before and after. This is the same class of concurrent load that produced all four freezes in the previous entry, run against the new path instead of raw ALSA.

  **Not yet done, and said plainly rather than claimed**: a real voice turn (TTS reply, not just the continuous silence stream) through this path under concurrent load, and a longer soak (tens of minutes, not 30 seconds) — freeze #2 from the earlier entry had no confirmed trigger at all, and a short clean run doesn't rule out a rarer failure mode. `docs/echo-show-8-freeze-scenarios.md` carries the full verdict table for all six scenarios and `docs/echo-show-8-audiotrack-design.md` the design + every bug found, in the order found, for whoever picks this back up.

- 2026-08-27 (**first fresh-provision test, via the new dashboard wizard rather than a script — the daemon started, ran, and silently died, all at once, with zero errors anywhere**): the actual first-time test the previous session's handoff called for — a factory-reset unit, wizard from scratch, nothing pre-existing to hide a gap. Two real bugs surfaced, neither crown-specific in the interesting sense (one lives in shared browser code, one in provisioning), both invisible until a device with genuinely nothing done to it by hand was put through the path.

  **First: the wizard's ADB authentication had never worked, on either device, ever.** `Transport.authenticate()` crashed mid-auth with `Cannot read properties of undefined (reading 'iterateKeys')`. Read `@yume-chan/adb@2.1.0`'s actual published source rather than guess: `authenticate()` takes a `credentialStore` — the object holding/generating the RSA keypair ADB signs the auth challenge with — and `dashboard.jsx` had only ever passed `authenticators`, never a store. Every call was one parameter short of working, on the shared `_ADB` module both wizards use, since the code was written. Fixed with a minimal `_WebCredentialStore` (WebCrypto keygen, private key in `localStorage`) rather than pulling in `@yume-chan/adb-credential-web` (incompatible key-shape API at its current `3.0.0-beta.2`). Full account in the root `JOURNAL.md` (2026-08-27), since it isn't crown-specific.

  **Second, and this one is genuinely new to a fresh device**: every step reported success, the device registered a pending row, TLS creds installed, the launcher app process came up, its playback and status-overlay sockets bound — and the daemon itself never ran. No crash, no log line, `ps` showed the app alive and nothing else. Root cause: `ServerService` execs the daemon as the app's own sandboxed uid (never root) and redirects its log to `/data/local/tmp/echomuse.log` via `ProcessBuilder`; on a device fresh from a factory reset that directory is `drwxrwx--x root:shell`, and the app uid has EXECUTE (enough to open a file that already exists) but not WRITE (not enough to create one) — so `ProcessBuilder.start()` throws, and `ServerService`'s `catch (IOException e) { stopSelf(); }` swallows it whole. **Every previous test unit had this permission loosened by hand, in some earlier session, and nobody had ever provisioned a truly fresh device through the app-launcher path before** — the exact same shape as the appops-after-reinstall trap from the previous session, a device-state assumption that held only because the same physical unit had been carrying it forward across sessions. Fixed by pre-creating the log file (`touch` + `chmod 666`) before starting the launcher — an existing file can be opened for write with only directory *execute*, so this sidesteps the missing directory *write* bit entirely — in both `provision_crown.sh` and the wizard's `start_launcher` step. Verified live: daemon registered and connected within 2 seconds of the fix.

  **Also found while fixing this**: `provision_crown.sh` had drifted from its own documented fix — still calling plain `am start-service`, which the 2026-08-26 entry above already found fails with "app is in background uid null" on a fresh install. The wizard's JS had the correct `am start-foreground-service`; the shell script didn't. Both now match.

  **State at end of THIS pass**: the wizard itself now runs clean start to finish on a fresh device with no manual steps. But the very next test — actually saying the wake word — surfaced a second, separate, still-open bug (below), so "full loop confirmed working" from earlier in this entry was premature; only provisioning is confirmed, not the voice loop.

- 2026-08-27, later (**a second fresh-provision run confirmed the wizard fix, then wake word never fired — and the real cause is upstream of wake-word selection entirely**): re-tested from another full factory reset specifically to prove the log-file fix works unattended, not just when patched by hand. It did — `am start-foreground-service` → daemon started, registered, connected, all through the wizard alone, no `adb shell` intervention. Confirms the previous entry's fix is real, not a fluke of the manual patch.

  **Then wake word (tried both `hey_jarvis` and the custom `Winston` model) never fired even once** — not a near-miss, not a low score, nothing. Confirmed via the controller's own DB row that config was correct (`owwModel` pointed at the right file, `owwOnDevice: off` — scoring is controller-side, so HA being unconfigured for this device is irrelevant to whether wake-word scoring itself runs; ruled that out explicitly before looking further, since it was the first guess). The controller log names the real symptom directly, repeating on every single connect cycle: `OWW: no mic frames for 10s on the continuous wake stream`, escalating through a defensive `mic_start`, then `mic_stop`+`mic_start`, and finally the control connection itself drops (`Control send failed: sent 1011 (internal error) keepalive ping timeout`) roughly 90–120s after every connect. **Mic frames are never reaching the controller at all** — wake-word model selection was never the problem; nothing was ever being scored because there was nothing arriving to score.

  Two live connect attempts both showed the identical pattern (10s → 10s → 30s escalation → forced disconnect), so this is not a one-off — it reproduces every time. Not yet root-caused: unknown whether `PcmMicrophone.Init()` is failing to open the capture device at all on this exact provisioning path (the device's own `/data/local/tmp/echomuse.log` was not captured for this specific failure before the session ended — the one log capture taken during troubleshooting was from an earlier restart before wake testing began, and didn't show a `[mic]` initialisation line at all, which is itself suspicious and worth checking for on the next attempt), or whether capture opens fine but frames die somewhere between the device and the controller. The recurring control-plane keepalive timeout is worth taking seriously as a possible SHARED symptom rather than a coincidence: a hung/blocked mic capture path could plausibly stall the same process enough to miss its own ping deadlines, which would make "no mic frames" and "control connection eventually dies" one root cause, not two.

  **Next session, in order**: (1) capture `/data/local/tmp/echomuse.log` from a fresh connect through to the point mic frames should start, specifically looking for whether `PcmMicrophone (crown) initialised` (or equivalent) ever logs at all; (2) if it does log successfully, the fault is between device and controller — check whether `mic_start` is actually being sent/received correctly on THIS provisioning path vs. the raw-shell-exec path every prior successful session used; (3) if it does NOT log, this is a capture-side init failure specific to something about the app-launcher execution context (uid/permissions/SELinux) that differs from a root shell exec, and the mic path needs the same kind of investigation the freeze bug got. Full voice loop is therefore **not yet re-proven** since the mic/speaker rewrite — only speaker output and daemon registration are confirmed on this exact provisioning path so far.

  **Correction, same day, before touching any code**: a spawned review raised the mic capture still bypassing the audio HAL (same collision class as the speaker freeze) as the likely cause — plausible on its own, but checked against the actual timeline and it doesn't fully hold. The user confirmed the full voice loop, wake word included, **worked this morning, on this same long-lived test unit, on this same `20260826-2201-dev` binary** — i.e. on the exact mic-raw-ALSA + speaker-AudioTrack combination the collision theory says shouldn't reliably work — **before** today's wizard-testing session started resetting the device. The failures above only began after the factory-reset-and-reprovision cycles began. That points at something a factory reset wipes which the daemon's own startup never re-applies — the same shape as both bugs already found and fixed today (the log-file permission, the appops grant) — rather than an architecture-level defect in the mic/speaker split. The audio-HAL-collision hypothesis isn't ruled out (worth checking regardless, since it's a real known ROM fragility), but it should not be treated as the leading explanation going into the next session — a fresh-device-state gap is now the stronger prior. Whatever check runs first next session should be chosen to distinguish between these two, not assume either.

  **Resolution, same day, minutes later: it was never a mic bug at all.** The "wake word doesn't work" testing that produced every symptom above was aimed at the wrong device — the user was speaking near an old Echo Dot (biscuit) sitting in the same room, and separately had HA/ESPHome pointed at the wrong Echo entity while setting that up. Once corrected (spoke at crown itself, HA integration confirmed against crown's own ESPHome entity), a real turn went through cleanly on the first try: `[G0916D10014507JS] Wake word detected (source=controller, score=0.727)` → `STT result: 'What is the time?'` → TTS generated, streamed, and played back, device-confirmed, in the controller's own log. Mic capture, wake scoring, ESPHome/HA integration and playback are all confirmed working end to end on this exact provisioning path, no code change needed.

  What this means for the two hypotheses above: **neither was tested against a real failure, because there wasn't one.** The "no mic frames for 10s" warnings earlier in this entry are real log lines and still worth understanding (a continuous wake stream delivering literally zero frames, even silence, for an extended period during the reset-cycle testing is not fully explained by "wrong device to speak at" — that would produce no wake detections, not zero frames arriving at all) — but they did not reproduce on the working connection, and are not blocking anything. Filed as a loose end, not a live bug: if it recurs, the diagnostics added this session (`PcmMicrophone (crown) initialised` log line, `internal/alsa`'s EPIPE-recovery counters) will make it much faster to tell apart from a genuine capture failure next time. Full voice loop is **re-confirmed working** since the mic/speaker rewrite — the earlier entries' "not yet re-proven" is superseded.
